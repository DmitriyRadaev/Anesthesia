# План миграции «АРМ Анестезиология» → Django REST Framework + React/TypeScript

## 1. Что было на входе

| Компонент | Технология | Каталог |
|-----------|------------|---------|
| Backend «Ядро» (Core) | **PHP 8 / Laravel 10**, Sanctum, PostgreSQL, maatwebsite/excel, Reverb | `core-test_clinic/` |
| Frontend «АРМ анестезиолога» | React 18 + TypeScript, MUI, MobX, tsyringe, RxJS, собственный webpack | `anesthesia-card-approbation/` |
| Документация API | 112 файлов `.docx` (по одному на endpoint) | `Описание API в Core/` |
| Коллекция Postman | `CORE.postman_collection.json` | корень |
| Схема «ЛК заведующего» | `Архитектура ЛК заведующего.drawio.png` | корень |

> **Противоречие №1.** В задаче исходный проект назван Java-проектом, но в репозитории нет ни одного
> `.java`/`pom.xml`/`build.gradle`. Backend написан на PHP/Laravel. Миграция выполнена с Laravel-проекта —
> именно он содержит всю бизнес-логику, модели и API, описанные в документации.

## 3. Этапы

1. Анализ кода и документации, фиксация противоречий (этот документ, раздел 4).
2. Backend: модели + миграции + фикстуры справочников → сервисы → сериализаторы → API → OpenAPI.
3. Авторизация: локальные пользователи, токены, роли, management-команды инициализации.
4. Frontend: Vite + React + TS + Tailwind; авторизация, реестр, карточки, ОС, протокол, наркозная карта,
   показатели, лаб. мониторинг, отчёты, админ-панель, печатные формы.
5. Удаление БАРС: проверка `grep -ri bars` по новому проекту.
6. Тесты (pytest + pytest-django на PostgreSQL; Vitest + Testing Library).
7. Postman-коллекция/окружение, README, документация.
8. Проверка «с нуля»: `docker compose up --build`.

## 4. Противоречия и принятые решения

| # | Противоречие / пробел | Решение |
|---|----------------------|---------|
| 1 | Проект назван Java, фактически PHP/Laravel | Мигрирован Laravel-проект |
| 2 | Миграция `_departments` не содержит `department_type_id`, но контроллер фильтрует по нему | Добавлено поле `department_type` (FK) |
| 3 | Миграция `protocol_redirecting_patient` содержит `deparment_picked_id/deparment_name_id`, а модель и документация — `department_type_id/department_id/doctor_fio` | Реализовано по документации и модели |
| 4 | `TubeInstallationPick`: модель хранит только `tube_installed/attempts`, документация — `tube_type_id/option/...` | Реализован полный набор полей из документации |
| 5 | Таблица `_doctor_fio` не создаётся ни одной миграцией (endpoint падал с 500) | `GET /api/catalogs/doctor_fio/` возвращает ФИО активных врачей из пользователей |
| 6 | Политика пользователей позволяла врачу/медсестре менять **собственную роль** (эскалация прав) | Управление пользователями — только Администратор/Заведующий/ИО; свой профиль — `/auth/me`, смена пароля |
| 7 | Политика пациентов не пускает Администратора к клиническим данным, а старый фронтенд пускал его в реестр | Администратор — технологическая роль: пользователи + отчёты, без доступа к медданным |
| 8 | Блоки протокола/карты в Laravel не проверяли роль (любой авторизованный) | Доступ только клиническим ролям (врач, медсестра, заведующий, ИО) |
| 9 | Ошибки бизнес-правил отдавались кодом `424` | Используется `409 Conflict` (нарушение состояния ресурса) |
| 10 | `PATCH` блоков карты фактически полностью заменял набор строк | Используется `PUT` (замена коллекции); `PATCH` оставлен для объектов 1:1 |
| 11 | `GET /patients/status/to_archive/{id}` — изменение состояния через GET | `POST /api/patients/{id}/archive/` и `/unarchive/` |
| 12 | `get_high_result_socket` — заглушка («This is text») | Не переносилась (нет функциональности) |
| 13 | CDSS endpoint был публичным и отдавал витальные показатели без авторизации | Токен пользователя или `X-API-Key` (`CDSS_API_KEY`) |
| 14 | Отчёт 41.10: в оригинале счётчики Local/General не обнулялись между операциями (ошибка накопления) | Подсчёт ведётся по каждой операции отдельно, покрыто тестом |
| 15 | Отмена ОС после изменения анестезиологических действий могла «оживить» отменённый ОС | Действия по отменённому ОС не меняют его статус |
| 16 | Лабораторный мониторинг в старом UI не сохранялся (нет API) | Добавлена модель `LabResult` и API |
| 17 | Поиск пациентов/пользователей в МИС БАРС | Удалён вместе с БАРС; пациенты создаются вручную, пользователи — администратором |
| 18 | Сидер шкалы Глазго содержал строки 16–20 из шкалы FOUR (дыхание) в разделе «Двигательная реакция» | Строки удалены: шкала Глазго — 15 позиций (4+5+6) |
| 19 | В печатной форме дозы в `ml` пересчитывались в `mg` (×1000) | mg/mcg/ng приводятся к mg, остальные единицы суммируются в своей единице |
| 20 | Отчёт 41.10 учитывал только ОС, у которых заполнен блок «Пациент передан» (INNER JOIN) | Учитываются все завершённые ОС со сведениями об анестезии; отсутствие блока = «не умер» |
| 21 | Нет отделений для типов «Линейное», «Реанимационное», «Пробуждения»; в справочнике вен нет «Кистевой вены», хотя UI её предлагал | Добавлены базовые записи (уточняются в django-admin) |
| 22 | ЦМС: для ЦВД «систолическое» бралось из MEAN, ключ ответа не совпадал с документацией | Значения SYS/MEAN/DIA берутся из соответствующих кодов, ключ `PRESS_BLD_VEN_CENT` |
| 23 | Дозы препаратов, объёмы растворов и потерь хранились строками (в т.ч. с запятой) | Числовые поля — decimal/float; API принимает и запятую, и точку |
| 24 | Первая версия нового интерфейса наркозной карты отличалась от исходной (вкладки с формами вместо таблиц) | Интерфейс карты перенесён с исходного: таблицы с ячейками времени (шаг 5/10/15 мин, рост ячеек до окончания анестезии), палитры пиктограмм (щелчок — предвыбор, двойной щелчок — установка, интервал дыхания — двумя двойными щелчками), исходные SVG-пиктограммы, модальные окна препаратов/растворов/потерь со «Итого», аккордеоны, единая кнопка «Сохранить» и «Очистить все» (заведующий/ИО); клиентские проверки порядка действий и этапов перенесены из `CellsGenerator.store.ts` |
| 25 | В исходной карте пиктограмма показывалась только при точном совпадении ЧЧ:ММ с ячейкой — при смене интервала часть данных «пропадала» | Пиктограмма показывается в ячейке, в интервал которой попадает время `[t, t + шаг)` |
| 26 | «Очистить все» в исходной системе сбрасывал дату и время поступления, а новый API не принимал `null` | `PATCH …/card/pid-datetime/` принимает `null` для даты и времени |
| 27 | Общий каркас нового интерфейса отличался от исходного (боковое меню, цвета, карточки) | Палитра и элементы исходного App.css перенесены в тему Tailwind (кнопки-«пилюли» с градиентом, поля, карточки с тенью); выдвижная боковая панель с иконками исходной системы; карточка пациента в реестре с цветной меткой статуса; блок пациента и навигация ОС как PatientBlock исходной системы |
| 28 | Протокол был набором карточек, Да/Нет — выпадающими списками | Разделы сгруппированы в 6 раскрывающихся блоков исходной системы с оглавлением; Да/Нет — плитки выбора (app-pickItem); восстановлен блок «Введенные препараты» (суммарные дозы из карты). Сохранение по блокам оставлено (в исходной системе — одной кнопкой) |
| 29 | Печатные формы отличались от исходных PDF | Карта: страницы по 30 пятиминутных интервалов (последняя — 26 + «Итого», «Ед. изм.»), шапка из 8 блоков, события/этапы/дыхание пиктограммами, график АД и пульса, ЧД, препараты, инфузии, потери, подвал с ФИО и номером страницы. Протокол: формулировки и порядок PDF исходной системы (A4) |
| 30 | Руководство пользователя (2024) и исходный код: при уходе с карты, протокола, лабораторного мониторинга и форм с несохранёнными данными должно появляться окно «Сохранение»; в новой версии данные терялись молча | Общая защита: переход по ссылке внутри приложения, выход из системы и закрытие вкладки при несохранённых изменениях требуют подтверждения («Остаться на странице» / «Перейти без сохранения»). Расхождения руководства, которые не ведут к потере данных (вид графиков, одна кнопка сохранения протокола, подписи кнопок), не переносились; описание ввода через окна в «Инфографике» и вход через БАРС в руководстве устарели |

## 5. Итог проверки

* Backend: 120 автотестов (pytest, PostgreSQL 16), `manage.py check`, `makemigrations --check`, генерация OpenAPI без предупреждений, `ruff`.
* Frontend: 51 автотест (Vitest), `tsc --noEmit`, `vite build`.
* Ручная проверка в браузере: вход врачом и администратором, реестр, наркозная карта (сохранение действия
  переводит ОС в «На операции»), графики, протокол, печатная форма, ограничение доступа к админ-панели.
* Наркозная карта после переноса исходного интерфейса проверена в браузере на реальном API: установка пиктограмм
  двойным щелчком, интервал дыхания, сохранение, добавление препарата через поиск по справочнику ЛС, ЦМС.
* Postman: коллекция из 98 запросов выполнена против работающего API, покрывает 100 % путей OpenAPI.
* Docker: `docker compose config` валиден; сборка образов в среде миграции не выполнялась (Docker Engine недоступен — нет WSL).
