# Архитектура

## Компоненты

```
 Браузер (React SPA)                         Шлюз мониторов Mindray eGateway        СППВР (CDSS)
        │  HTTPS, Bearer-токен                        │ TCP, HL7 v2 (MLLP)               │ X-API-Key
        ▼                                             ▼                                  │
 ┌──────────────┐  /api/*   ┌────────────────────────────────┐   ┌──────────────────┐   │
 │ nginx        │ ────────► │ Django + DRF (gunicorn)        │   │ hl7_listener     │   │
 │ (frontend)   │           │  accounts · catalogs · patients│   │ (management cmd) │   │
 └──────────────┘           │  operations · protocol · card  │◄──┴──────────────────┘   │
                            │  monitoring · labs · reports   │◄─────────────────────────┘
                            └───────────────┬────────────────┘
                                            ▼
                                     PostgreSQL 16
```

* **Frontend** — SPA на React/TypeScript. Данные загружаются через TanStack Query (кеш, состояния загрузки и ошибок),
  формы — управляемые компоненты с клиентской валидацией, дублирующей серверную. Маршруты защищены по ролям.
* **Backend** — DRF API. Разделение ответственности:
  * `models.py` — структура данных и ограничения целостности (FK, уникальность, диапазоны);
  * `serializers.py` — формат API и валидация входных данных;
  * `services.py` — бизнес-правила и сценарии (статусы пациента/ОС, отмена/завершение, расчёты доз, ЦМС, отчёты);
  * `views.py` — HTTP-слой: права доступа, фильтрация, пагинация, OpenAPI-описание.
* **Ошибки** — единый формат `{"detail", "code", "errors?"}` (`apps/common/exceptions.py`); нарушения бизнес-правил — `409 Conflict`.
* **Конфигурация** — только через переменные окружения (`config/settings.py`, `.env.example`).

## Бизнес-процессы

### Карточка пациента

| Статус | Значение | Переход |
|--------|---------|---------|
| 1 — Новая | создана, ОС не было | при создании карточки |
| 2 — Активная | идёт операционный случай | при создании ОС; при изменении анестезиологических действий; «вернуть из архива» |
| 3 — Архивная | ОС завершён или отменён | при завершении/отмене ОС; «в архив» (запрещено при ОС «Поступил»/«На операции») |

Пациент уникален по ФИО + дате рождения + полу. Удаление — только руководителями и только без ОС.

### Операционный случай (ОС)

```
            создание ОС                «Начало анестезии» в карте
 (пациент не «Активная» и нет          ┌──────────────────────┐
  активных ОС)  ───────────► ПОСТУПИЛ ─┤                      ▼
                                │      └────────────── НА ОПЕРАЦИИ
                  отмена        │      удаление «Начала        │
         (нет «Начала анестезии»)│      анестезии»              │ завершение
                                ▼                              ▼ (есть «Окончание анестезии»)
                            ОТМЕНЁН                         ЗАВЕРШЁН
                    (пациент → «Архивная»)           (пациент → «Архивная»)
```

* Создавать/изменять ОС могут заведующий/ИО (с любым врачом) и врач (только назначая врачом себя).
* Отменить/завершить — заведующий/ИО или врач, назначенный на ОС. Удаление ОС не предусмотрено.
* Врач и медсестра назначаются на ОС (FK `doctor`/`nurse`); проверяется соответствие роли и активность.

### Протокол анестезии и наркозная карта

Блоки привязаны к ОС: `/api/operations/{id}/protocol/<блок>/` и `/api/operations/{id}/card/<блок>/`.
Блоки «один к одному» (премедикация, ИВЛ, передача пациента…) — `GET`/`PUT`/`PATCH`; наборы строк
(действия, препараты, инфузии, венозный доступ…) — `GET`/`PUT` (полная замена набора, в транзакции).

Время в карте вводится как ЧЧ:ММ и относится к суткам карты: время раньше поступления относится к следующему дню.
Шкала карты — 5-минутные интервалы от «поступление − 5 мин» до «Окончания анестезии» (или текущего момента), не более суток.
Сервер проверяет: «Начало/Окончание анестезии» — не более одного раза, окончание позже начала; интервалы одного
препарата/раствора/типа дыхания не пересекаются (с точностью до минуты; инфузия без окончания — продолжается).

Итоговые дозы: mg/mcg/ng приводятся к mg, остальные единицы (ml, Ед, ME, об.%) суммируются отдельно.

### Мониторинг (HL7)

`hl7_listener` принимает поток MLLP от eGateway, разбирает сегменты PID/PV1/OBR/OBX и сохраняет
`HL7Result(observation_at, pid, order_number, observations[])` (повторное сообщение перезаписывается).
Альтернатива — `POST /api/monitoring/hl7/`. Данные связываются с ОС по полю `pid`. Используются в:
графиках (`/monitoring/results/` с инкрементальной подгрузкой), блоке ЦМС карты (последнее сообщение в каждом
5-минутном интервале), печатной форме (АД/пульс/ЧДД), СППВР (`/api/cdss/result/{id}/`).

### Отчёт 41.10

По завершённым ОС за период: эпидуральная и спинальная анестезия (по методам местной анестезии),
сочетанная (местная + общая) — в разрезе неотложных/экстренных/плановых операций и летальности; строка «Всего».
Формирование — `GET /api/reports/4110/` (Excel) или `/api/reports/4110/data/` (JSON для предпросмотра).

## Безопасность

* Пароли — хеши PBKDF2 (стандарт Django), политика сложности — валидаторы Django.
* Токены — случайные 256-бит, в БД хранится только SHA-256; срок жизни `AUTH_TOKEN_TTL_HOURS`;
  выход отзывает текущий токен; смена пароля/деактивация завершают остальные сеансы.
* Ограничение частоты попыток входа (`LOGIN_THROTTLE_RATE`), запросов СППВР (`CDSS_THROTTLE_RATE`).
* Интеграционный ключ сравнивается за постоянное время; без ключа интеграционные endpoints доступны только по токену.
* Секреты — только в `.env` (не коммитится); в репозитории — `.env.example` с заглушками.

## Ограничения

1. **Исходный проект — PHP/Laravel, а не Java** (в задаче указан Java) — мигрирован фактический код.
2. Окружение, в котором выполнялась миграция, не имело рабочего Docker (WSL недоступен): `docker compose config`
   проверен, образы собраны не были. Backend и тесты проверены на PostgreSQL 16 напрямую.
3. Печатные формы реализованы как печатные HTML-страницы (печать / «Сохранить как PDF» браузера) вместо генерации PDF
   на клиенте библиотекой `@react-pdf` в старом UI.
4. Real-time поток показателей через WebSocket (Laravel Reverb, режим high resolution) в исходной системе был
   заглушкой и не переносился; графики обновляются опросом каждые 30 с.
5. Блоки «Установка трубок» и «Ларингеальные маски» сохранены в API для совместимости, в UI используется
   объединённый блок «Обеспечение проходимости дыхательных путей» (как и в исходном UI).
6. Поиск пациентов и сотрудников во внешней МИС удалён вместе с БАРС; при необходимости интеграции с МИС её следует
   реализовать отдельным модулем импорта.
7. Справочники отделений для типов «Линейное», «Реанимационное», «Пробуждения» в исходных сидерах отсутствовали —
   добавлены базовые записи, их следует уточнить для конкретной клиники (Django admin).
